# 배경 부하 주입

서버 부하는 제안서 §5.2의 실험 요인 중 하나(Idle / 30% / 50% / 70% CPU — 제안서의
30/65/90에서 재정의, 아래 참조)이고,
**외생 변수여야 한다** — 렌더 모드가 서버 부하를 바꾸는데 그 부하가 동시에 피처이기
때문이다. 부하가 측정 대상에 반응하면 인과 방향이 닫힌 고리가 된다.

## 구성

| 파일 | 역할 |
|---|---|
| `profile.json` | 라우트 믹스·목표 CPU. **k6와 로컬 생성기가 둘 다 읽는다** |
| `background.js` | k6 스크립트 — 배포(ECS Fargate Spot)용 산출물 |
| `generator.mjs` | 로컬 대체 생성기. k6 바이너리 없이 같은 믹스를 재현한다 |
| `calibrate.mjs` | 목표 CPU에 도달하는 VU 수를 이진 탐색 → `calibration.generated.json` |

로컬 생성기를 따로 두는 이유는 단순하다: 이 개발 환경에 k6가 없다. 두 생성기가 **같은
`profile.json`을 읽게** 한 것이 핵심이다 — 믹스 정의가 갈라지면 로컬에서 캘리브레이션한
VU 수를 배포에 옮길 수 없고, 그러면 "부하 65%"라는 셀 이름이 두 환경에서 다른 것을 뜻하게
된다.

## 캘리브레이션

```bash
# 앱을 프로덕션 빌드로 띄운 뒤
node calibrate.mjs                 # → calibration.generated.json
```

이 개발 머신(할당 코어 1, 머신 18코어)에서의 결과 — **목표가 30/65/90이던 시절의 값**이다:

| 수준 | 목표(당시) | VU | 실측 CPU |
|---|---|---|---|
| idle | — | 0 | 0.3% |
| low | 30% | 6 | 31.1% |
| mid | 65% | 30 | 62.8% |
| high | 90% | 71 | 91.9% |

본수집(`grid-v1`, Fargate 2 vCPU, `SUT_CPU_CORES=2`)에서 워커가 실행 시점에 다시 잡은 값:

| 수준 | 목표 | VU | 지속 CPU |
|---|---|---|---|
| low | 30% | 40–56 | 28.5–32.5% |
| mid | 50% | 96–192 | 46.2–51.7% |
| high | 70% | 512 (상한) | 63.8–68.9% |

### 목표가 30/65/90에서 30/50/70으로 바뀐 이유

단일 프로세스 `next start`는 2 vCPU 태스크에서 CPU **~71%가 천장**이다 — VU 512→66–71%,
1024→62%(라우트별 RPS가 512와 동일: 처리율 포화, 추가 VU는 큐잉만), 2048→
`/api/internal/metrics`가 응답을 못 해 캘리브레이션 자체가 죽는다(grid-v1 5차 실행의
사인). 90%는 물리적으로 도달 불가라 2026-08-14에 목표를 재정의했고, `search.mjs`의
`maxVus`도 2048→512로 내렸다(상한의 기준은 "CPU가 더 오르는가"가 아니라 "SUT가 관측
가능한 채로 남는가"). high는 그래도 천장에 걸려 허용오차(±4)를 1–2%p 벗어난 샤드가 있다
— **셀에는 목표가 아니라 실측 지속 CPU가 기록**되므로 라벨은 정직하고, "목표 미달"
경고는 이 수준에서 예상된 출력이다. 이전 로컬 실측 "VU 512→85%, 1024→97%"는 18코어
호스트에서 여유 코어가 GC·libuv에 쓰이던 값이라 이 태스크 크기에서는 성립하지 않는다.

**이 값을 다른 환경에 그대로 쓰면 안 된다.** VU↔CPU 관계는 하드웨어·라우트 믹스·Node
버전에 따라 달라지므로 환경마다 다시 돌려야 한다. `allocatedCores`·`machineCores`·
`generatedAt`이 산출물에 함께 기록되는 것은 어느 환경의 값인지 나중에 판별하기 위해서다.

**측정 중에는 VU 수를 얼린다.** CPU를 피드백 제어하지 않는다 — 제어기가 붙으면 부하가
측정 요청에 반응하게 되어 외생성이 깨진다. 같은 이유로 배포에서는 오토스케일링을 끄고
`desiredCount`를 고정한다.

목표에 도달하지 못하면 로컬 `calibrate.mjs`는 **실패로 종료한다.** 원격 캘리브레이션
(`workers/lib/loadControl.mjs`)은 경고를 남기고 **실측 지속값**을 기록한 채 진행한다 —
도달 여부와 무관하게 셀에 남는 것은 실측 CPU라 셀 정의가 거짓이 되지 않는다.

## 설계상 지켜야 하는 것

- **부하 라우트와 측정 라우트를 겹치지 않게 둔다.** 같은 라우트에 부하를 걸면 그 라우트의
  `rps_r`과 캐시 상태가 부하에 의해 결정되어, 셀 변수로 고정한 값과 어긋난다.
- **부하는 강제 지정 경로(`/m/…`)로 보낸다.** 결정 계층을 거치면 추론 비용이 부하에 섞여,
  측정 요청이 겪는 CPU가 렌더 부하인지 결정 부하인지 분리되지 않는다.
- **k6의 응답 시간을 Web Vitals로 쓰면 안 된다.** k6는 렌더하지 않는다. 부하 셀과 측정 셀은
  분리된 계층이다(설계 문서 §11-6).
- **본문을 끝까지 읽는다.** 버리면 서버가 스트리밍을 중단해 부하가 실제보다 가벼워진다.
- **부하 %의 분모는 머신 코어가 아니라 할당 CPU다.** 제안서의 "30/65/90% CPU"(현재 30/50/70)는 Fargate
  태스크에 할당된 vCPU 대비 사용률이다. 머신 전체 코어로 나누면 단일 스레드 Node 프로세스는
  18코어 머신에서 상한이 5.6%가 되어 30%조차 도달할 수 없다. `SUT_CPU_CORES`로 분모를
  맞추고(기본 1), 그 값을 `calibration.generated.json`에 함께 기록한다 — 분모가 다르면
  "부하 65%"가 두 환경에서 다른 것을 뜻한다.
- **하드웨어가 바뀌면 다시 캘리브레이션한다.** VU↔CPU 관계는 하드웨어·라우트 믹스·Node
  버전에 따라 달라진다. `calibration.generated.json`에 생성 시각과 대상을 기록해 둔다.
