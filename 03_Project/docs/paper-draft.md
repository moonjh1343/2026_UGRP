## Abstract

웹 프레임워크는 라우트마다 렌더링 모드(CSR·SSR·SSG·Streaming SSR·Islands)를 빌드 시점에 고정한다.
그러나 어떤 모드가 사용자 경험(QoE)과 서버 비용 면에서 최선인지는 요청 시점의 디바이스 성능, 네트워크
품질, 서버 부하에 따라 달라진다. 본 연구는 최적 모드를 런타임 컨텍스트의 함수로 보고, 요청마다 모드를
고르는 정책을 학습·서빙하는 시스템을 설계·구현·평가한다. 하나의 Next.js 코드베이스에 다섯 모드를 동일
DOM으로 구현한 벤치마크 앱(SUT)을 두고, 디바이스 4 × 네트워크 5 × 서버 부하 4 조건 격자에서 라우트별
실행 가능 모드 전부를 30회씩 측정하는 완전 요인 실험(10,400셀, 311,108행)을 AWS Fargate 20샤드로 수행했다.
비용 `J(x,m) = Σw·z_r(QoE) + λ·ServerCost`를 LightGBM 서로게이트로 회귀하고 argmin으로 모드를 고르며,
λ는 예산 제약의 그림자 가격으로 해석한다. 라우트 홀드아웃 400조건에서 서로게이트 정책은 top-1 74.8%,
평균 regret 0.041로, 최선의 고정 모드(regret 0.495)와 규칙 기반 휴리스틱(0.447)을 10배 이상 앞섰다.
λ 스윕은 λ=0.3에서 QoE 손실을 거의 내지 않고 서버 렌더 비용을 λ=0 대비 52% 줄이는 파레토 무릎을
보였다. 앙상블을 깊이 12 트리로 증류(R² 0.999, 잎 2,724, 687KB)해 Lambda@Edge에 내장했고, 추론 p95는
0.025ms로 TTFB 예산 2ms의 1%대다. 조용히 실패하는 측정·서빙 버그들과 이를 막는 게이트도 함께 보고한다.

## 1. 서론

### 1.1 배경

Next.js·Nuxt·Astro 같은 현대 프레임워크는 CSR, SSR, SSG/ISR, Streaming SSR, Islands 등 여러 렌더링
모드를 제공하지만, 선택 단위는 **라우트, 시점은 빌드**다. 개발자는 "이 페이지는 SSG, 저 페이지는 SSR"을
정적으로 정하고 배포하며, 그 결정은 플래그십 폰에서 5G로 접속한 사용자와 저사양 기기에서 3G로 접속한
사용자에게 동일하게 적용된다. 기존 CSR-vs-SSR 비교 연구들[B]은 대개 단일 조건에서 두세 모드를 재고,
"SSR이 빠르다" 류의 고정된 결론을 내린다.

### 1.2 문제 제기

렌더링 모드의 비용 구조는 조건에 따라 뒤집힌다. CSR은 JS 번들 다운로드·실행이 클라이언트에 실리므로
저사양·저대역폭에서 불리하지만 서버 CPU는 거의 쓰지 않는다. SSR·Streaming은 TTFB가 서버 부하에 민감하다.
SSG는 캐시가 뜨거우면 압도적이지만 캐시 상태에 종속된다. Islands는 하이드레이션 CPU를 줄이지만
서버 렌더 비용은 SSR과 같다. 즉 최적 모드 `m*`는 컨텍스트 `x`(디바이스·네트워크·서버 상태·라우트 특성)의
함수이며, 이를 빌드 타임 상수로 두는 것은 구조적 손실이다.

### 1.3 연구 질문 및 기여

- **RQ1** 조건에 따라 모드 우열이 실제로 갈리는가(divergence)?
- **RQ2** 학습된 정책이 고정 모드·프레임워크 기본값·휴리스틱 규칙을 이기는가?
- **RQ3** 엣지 추론 오버헤드(TTFB 증가 < 2ms)와 캐시 효율을 유지하며 서빙할 수 있는가?

기여는 다음과 같다.

1. 다섯 렌더링 모드를 **동일 DOM·동일 컴포넌트 그래프**로 구현한 단일 코드베이스 SUT와, 렌더 결정과
   브라우저 측정을 상관 ID로 조인하는 계측 설계(§4).
2. 반사실(counterfactual) 문제를 실험 설계로 우회하는 완전 요인 랩 수집 — 10,400셀 × 30반복, 20샤드
   병렬, 외생적 배경 부하, 재현성 통제(§5). 데이터셋 자체가 기여물이다.
3. 서로게이트 회귀 + argmin 정책, λ의 그림자 가격 해석, 라우트별 z-정규화 레이블, 깊이 12 트리
   증류(§3, §6)와 그 평가 — 정책 top-1 74.8%, regret 0.041, 베이스라인 대비 10배 이상 개선(§7).
4. CloudFront 캐시 키를 클라이언트 힌트 버킷 하나로 접고 origin-request 시점에 추론하는 엣지 서빙
   설계 — 캐시 히트는 추론 비용을 내지 않으며 미스 경로 추론 p95 0.025ms(§4.4, §7.6).
5. 실험 시스템에서 "조용히 통과하는" 실패 목록과 각각의 방어 게이트(§8.3).

### 1.4 논문 구성

2장 관련 연구, 3장 정식화, 4장 시스템, 5장 실험 설계, 6장 학습, 7장 평가, 8장 논의, 9장 결론.

## 2. 관련 연구

### 2.1 CSR vs SSR 정적 비교

Iskandar et al.[B], Teknika(2024)[B]를 비롯한 비교 연구들은 CSR/SSR/SSG의 로딩 시간을 재지만 단일 조건에서
측정한다. 국내 연구(SSR vs Streaming SSR 하이드레이션 분석)[B]도 같은 한계를 가진다. 이들은 본 연구의
RQ1이 "조건별로 결론이 역전된다"를 보이는 배경이 된다.

### 2.2 조건 적응형 렌더링·하이드레이션

가장 가까운 선행기술은 US 10,764,403[A]으로, 클라이언트 자원과 서버 이용률을 보고 SSR 여부를 정하는
규칙 기반 방식이다 — 문제 설정은 거의 같으나 학습·평가가 없다. MRAH[A]는 디바이스·네트워크·컴포넌트
중요도로 하이드레이션 순서를 조정하지만 모드 선택이 아니며 서버 부하 축이 없다. Osmani의 Adaptive
Loading[A]은 Network Information API·Device Memory·Client Hints로 경험을 차등 제공하는 클라이언트
휴리스틱으로, 본 연구 특징 벡터의 원형이다. Energy-aware Web Browsing[A]은 회귀로 로드 시간을 예측한
뒤 argmin을 취하는 구조가 같지만 대상이 big.LITTLE 코어 선택이다.

### 2.3 웹 성능 예측·ML 기반 시스템 최적화

웹 성능 예측 모델 비교[D]는 트리 앙상블이 선형·SVM·MLP보다 안정적임을 보여 LightGBM 선택의 근거가 된다.
Pensieve[E]는 런타임 컨텍스트로 전송 정책을 학습하는 계열의 대표이며, CherryPick·Scout·Micky[E]는 성능
모델로 "충분히 좋은 구성"을 고른다 — 본 연구의 top-1/top-2 마진 논리와 통한다. Polaris·Prophecy·Shandian
·Klotski[C]는 페이지 로드를 시스템 수준에서 최적화하는 계보로, Streaming SSR의 시스템적 원형이다.

### 2.4 오프폴리시 평가와 반사실 문제

필드 데이터는 요청마다 하나의 모드만 관측되므로 다른 모드의 결과는 반사실이다. Li et al.[E], Dudík et
al.[E], Swaminathan & Joachims[E]의 IPS/DR/CRM은 성향 로깅된 무작위화 트래픽에서 비편향 평가를 가능하게
한다. 본 연구는 **랩 수집에서는 완전 요인으로 반사실을 직접 관측**하고, 필드 무작위화(5–10%)를 후속
OPE용으로 설계에 남긴다(§5.6).

**공백.** 어느 문헌도 (a) 5개 모드를 한 SUT에서 (b) 디바이스×네트워크×서버 부하 격자로 측정하고
(c) 서로게이트 회귀+argmin 정책을 학습해 (d) 엣지에서 <2ms로 서빙하는 조합을 다루지 않는다.

## 3. 문제 정식화

### 3.1 컨텍스트, 모드 집합, 실행 가능성

컨텍스트 `x`는 (i) 클라이언트: 디바이스 등급, `deviceMemory`, `hardwareConcurrency`, 유효 네트워크
유형(ECT), RTT, downlink, saveData, 이전 세션 LCP/TBT; (ii) 서버 상태: CPU%, 이벤트 루프 p95, inflight,
캐시 적중률, 라우트 RPS; (iii) 라우트 정적 특성: 노드 수, 상호작용 요소 수, 페이로드 KB, fetch 깊이·
지연, 개인화 비율, SEO 가중치, 번들 KB; (iv) 재방문 여부 — 총 23개 특징이며 모드 인덱스가 앞에 붙는다
(`policy/features.ts`, 부록 B).

모드 집합 `M = {csr, ssr, stream, ssg, islands}`이고, 라우트 `r`의 실행 가능 집합 `M(r) ⊆ M`이다.
SSG는 개인화·대시보드·폼 유형에서 제외된다(`Σ_r |M(r)| = 110`, 라우트 25개). 정책이 실행 불가 모드를
조용히 폴백하면 베이스라인으로 쓸 수 없으므로, `decide()`는 폴백을 `x-decision-reason: infeasible`로
기록한다.

### 3.2 비용 함수

    J(x, m) = Σ_i w_i · z_r(QoE_i(x, m)) + λ · ServerCost(x, m)

QoE 지표는 LCP·INP·TBT·TTFB, 가중치 `w = (0.4, 0.3, 0.2, 0.1)`(Core Web Vitals의 상대 비중을 따르며
스윕 대상). `ServerCost`의 일반형은 `C_render(m)·missRate(x,m) + C_serve(m) + μ·C_store(m)`이다.

### 3.3 제약 최적화와 λ

운영 목표는 `min E[QoE 비용] s.t. E[ServerCost] ≤ B`이며, 라그랑주 완화의 승수 λ가 서버 CPU 1ms의
**그림자 가격**이다. λ는 하이퍼파라미터가 아니라 배포 후 이중 상승법(dual ascent)으로 예산 B에 맞춰
조정되는 값이고, 오프라인에서는 λ 스윕으로 QoE–비용 파레토 곡선을 그린다(§7.4).

### 3.4 서로게이트 회귀 + argmin

정책은 `π(x) = argmin_{m ∈ M(r)} Ĵ(x, m)`이다. 직접 분류를 택하지 않은 이유는 두 가지다. (1) 분류
레이블은 사람이 정한 임계로 만들어야 하고, (2) "모드들이 비슷해서 전환할 가치가 없다"를 표현할 수
없다. 모드 전환에는 캐시 파편화 등 고정 비용이 있으므로 top-1과 top-2의 예측 마진이 결정에 실린다
(§7.3에서 마진 분포를 보고한다). 학습 목적은 순수 회귀와 pairwise 순위 손실의 혼합(`α`)이며, 정책이
쓰는 것은 절대값이 아니라 조건 내 순서이기 때문이다.

### 3.5 라우트별 z-정규화

QoE를 라우트별로 z-정규화하지 않으면 모델은 "무거운 페이지 = 나쁨"을 학습해 라우트 간 분산을 설명하는 데
용량을 쓰고, 정작 목표인 **같은 라우트 내 모드 간 차이**는 뭉개진다. 표준편차 0인 라우트는 z=0.

## 4. 시스템 설계

### 4.1 전체 아키텍처

제안서가 정의한 다섯 플레인 — SUT, 클라이언트 측정, 부하 주입, 데이터, 학습·서빙 — 을 구현했다.
랩 경로: Fargate 위 SUT ↔ k6 부하 태스크 ↔ Playwright 워커 삼중이 한 샤드를 이루고 20샤드가 독립
실행되며, 결과는 셀당 NDJSON 하나로 S3에, 체크포인트는 DynamoDB에 쓴다. Step Functions Distributed
Map이 셀 격자를 오케스트레이션한다. 서빙 경로: `ServingOrigin`(ap-northeast-2, ALB+SUT) 앞에
`Serving`(us-east-1, CloudFront + CloudFront Function + Lambda@Edge).

### 4.2 벤치마크 애플리케이션(SUT)

Next.js 16 App Router 단일 코드베이스에 `/m/{mode}/{type}/{key}` 강제 경로와 정책 경로를 두고, 다섯 모드가
**같은 컴포넌트 그래프**를 공유하도록 했다. 라우트 유형은 content·list·dashboard·form·personalized
5종, 각 유형 5인스턴스(총 25라우트). 모드 간 최종 DOM 동일성은 `check:dom`, 페이로드 바이트 동일성은
`check:determinism`, Islands에 서버 전용 트리가 클라이언트 번들에 없음을 `inspect:graph`가 검증한다.
서버는 요청별 렌더 CPU(µs)·벽시계·렌더 횟수·캐시 상태를 응답 헤더로 노출한다.

### 4.3 결정 계층(policy)

`policy/`는 `app/`·`node:*`를 임포트하지 않는 순수 모듈로, Lambda@Edge와 SUT 양쪽에서 같은 코드가 돈다
(`check:policy`가 경계를 강제). 크롤러 UA와 결제·인증 라우트는 SSR로 하드 핀 — ML은 SEO·정확성을
결정하지 않는다. 서킷 브레이커는 하이드레이션 오류·5xx 급증 시 전 트래픽을 기본 모드(Streaming SSR)로
되돌린다. 마진 임계 `τ = 0.05`.

### 4.4 엣지 서빙

**캐시 키가 설계의 전부다.** CloudFront Function이 viewer-request에서 Client Hints를 소수의 버킷으로
접어 `x-ugrp-bucket` 헤더 하나를 만들고, 그 헤더만 캐시 키에 넣는다. 결정은 origin-request(=캐시 미스)
에서만 돌므로 캐시 히트는 추론 비용을 전혀 내지 않고, 미스 경로는 어차피 오리진 렌더(수십~수백 ms)가
지배해 2ms 예산이 여유롭다. 증류 트리는 AppConfig 대신 번들에 내장했다 — Lambda@Edge에는 환경변수가
없고 콜드 스타트 시 fetch가 요청 경로에 놓이며, 빠른 롤백은 서킷 브레이커의 몫이기 때문이다. 서버 상태
특징은 의도적으로 ~30초 stale이다.

### 4.5 상관 ID 조인

렌더 결정은 엣지/서버에서, 측정은 브라우저에서 일어난다. 서버 레코드(cid, 모드, 결정 이유, 렌더 CPU)와
`web-vitals/attribution` 비콘(cid, LCP·INP·TBT·TTFB·CLS)이 `cid`로 조인되지 않으면 데이터셋은 무가치하다.
`check:join`이 이 경로를 게이트한다.

### 4.6 계획서 대비 설계 변경

| 제안서 | 구현 | 이유 |
|---|---|---|

## 6. 학습 파이프라인

### 6.1 특징 벡터와 train-serve 정합성

`training/config.py`의 `FEATURE_ORDER`는 `policy/features.ts`의 `toVector()` 사본이다. 자동 동기화가
없으므로 `check:tree`가 게이트다: 트리의 특징명이 `toVector()`에 없으면 서빙에서 `x[feature] ?? 0`이
조용히 0을 읽어 모든 요청이 왼쪽 가지로 간다. 랩이 시뮬레이션하지 않는 특징(deviceMemory 등)은 고정
기본값(§부록 B).

### 6.2 레이블링

QoE 항은 §3.2. ServerCost는 세 곳에서 측정 가능한 것으로 대체했다: (i) `missRate` 공식 대신 **관측된
렌더 발생 여부**(배경 부하가 측정 라우트를 피하므로 `rps_r`이 무의미), (ii) 행별 `serverRenderCpuUs`
대신 (모드, 라우트 유형)별 idle 셀 N-반복 평균(타이머 양자화), (iii) `C_serve`·`C_store`는 **0 — 근사가
아니라 미계측**. 단위는 µs→ms. 그 결과 모드별 평균 서버 비용은 ssg 0, csr 2.35, ssr 3.37, islands 3.46,
stream 5.14 ms다.

### 6.3 서로게이트

LightGBM × 5시드 앙상블, 200 라운드, 회귀+pairwise 혼합 α=0.3. 학습 248,886행 / 검증 62,222행.

### 6.4 증류

앙상블 예측 `Ĵ`를 타깃으로 단일 결정 트리를 학습한다. 제안서는 깊이 5(~50KB)를 상정했으나 λ<1에서는
문맥 상호작용 때문에 부족해(§7.7) **깊이 12, 잎 2,724, 687KB**로 확장했다. `check:tree`·`check:policy`
통과 후 `policy/model/tree.v0.json`으로 교체(`trained-20260818T163155Z`).

### 6.5 분할

시간 + 라우트 그룹 분할을 의도했으나, 완전 요인에서는 모든 라우트가 수집 창 전체에 걸쳐 시간 분할이
퇴화한다. 파이프라인은 이를 경고하고 라우트 그룹 단독 분할로 폴백한다 — 이 분할에는 시간 누수 방어가
없다(§8.2). 검증은 홀드아웃 라우트 5개 × 80조건 = **400조건**.

## 7. 평가

### 7.1 지표

조건(라우트×디바이스×네트워크×부하) 단위로 (a) top-1: 정책 선택이 관측 최적과 일치하는 비율, (b) regret:
`J(chosen) − J(oracle)`의 평균·중앙값·p95, (c) pairwise accuracy: 모드 쌍 순서 정확도, (d) 선택된 모드의
QoE 항·서버 비용(ms).

### 7.2 베이스라인

고정 모드 5종, 프레임워크 기본값(Streaming SSR = fixed-stream), 규칙 기반 휴리스틱(디바이스·네트워크
임계 규칙), oracle. fixed-ssg는 실행 가능한 160조건에서만 평가.

### 7.3 RQ1 — 조건별 divergence

QoE만으로(λ=0) 조건별 최적 모드를 보면 islands 30.6%, ssr 27.8%, stream 15.6%, ssg 13.3%, csr 12.6%로
분산되며, **25개 라우트 전부가 조건에 따라 승자가 바뀐다.** 축별 역전의 예:

- **네트워크.** content 라우트에서 csr이 최적인 비율은 lte 44%, 5g 40%이나 3g-slow·offline-first에서는
  **0%**; 같은 조건에서 stream·islands가 올라온다. LCP 중앙값은 csr이 5g 1,036ms → offline-first
  9,388ms로 9배 벌어지는 반면 ssr은 540 → 2,252ms(4배).
- **디바이스.** list 라우트에서 ssg 최적 비율이 flagship 45% → very-low 12%로 떨어지고 islands가
  14% → 47%로 오른다(TBT 중앙값 flagship 0ms vs very-low 285–368ms — 하이드레이션 CPU가 지배).
- **서버 부하.** content 라우트에서 ssg 최적 비율이 idle 8% → high **67%**, list 11% → 57%. TTFB
  중앙값이 high에서 ssr/stream/islands 1,700ms vs ssg 618ms.
- **캐시 불가 라우트**(dashboard·personalized)는 islands·ssr가 양분하되 very-low에서 islands 우세.

top-1과 top-2의 J 마진(λ=0.3)은 중앙값 0.488, p25 0.131, **21.8%의 조건이 마진 < 0.1**로 "전환할
가치가 없는" 구간이 실재한다 — 마진 임계 τ가 필요한 이유다.

## 8. 논의

### 8.1 해석과 실무 함의

(1) "SSR이 CSR보다 빠르다"는 조건 의존적이다 — 좋은 네트워크의 content 라우트에서는 csr이 40%
이상에서 최적이며, high 부하에서는 ssg가 아니면 어떤 서버 렌더도 TTFB 1.7초를 낸다. (2) 정적 라우트
설정이 낼 수 있는 최선(fixed-ssg 실행 가능 구간)은 정책이 그대로 재현하면서, 나머지 60% 라우트에서
regret을 10배 이상 줄인다. (3) λ는 운영자가 예산으로 정하는 값이고, 0.3 근처가 "QoE를 거의 잃지 않고
서버 절반"인 구간이라는 것이 이 SUT의 결과다.

### 8.2 위협 요인

- **에뮬레이션 vs 실기기.** CDP 스로틀은 CPU 배수이지 실기기 특성이 아니다. Device Farm 서브셋 미수행.
- **부하 캘리브레이션.** high는 목표 70%에 실측 63.8–68.9%, 표본 손실 있음. 부하 축 레이블은 실측값.
- **단일 SUT.** 라우트 25개, 유형 5종. 라우트 홀드아웃 일반화만 검증.
- **시간 분할 부재.** 완전 요인 특성상 시간 누수 방어 없음.
- **서버 비용 미계측 항.** `C_serve`·`C_store`=0, `missRate`는 관측 대체. 절대 서버 비용은 과소.
- **필드 검증 없음.** OPE·캐시 적중률·서킷 브레이커 발동은 미측정.

### 8.3 조용히 통과하는 실패와 게이트

| 실패 | 증상 | 게이트 |

## 9. 결론 및 향후 연구

렌더링 모드를 런타임 컨텍스트의 함수로 보고, 완전 요인 랩 데이터(10,400셀·311k행)로 서로게이트 회귀
정책을 학습해 엣지에서 0.025ms에 서빙하는 시스템을 보였다. 정책은 프레임워크 기본값 대비 regret 22배,
최선 고정 모드 대비 12배를 줄이며, λ=0.3에서 서버 렌더 비용을 절반으로 줄인다. 향후: 서빙 플레인
재배포와 필드 무작위화·OPE, 이중 상승법으로 λ 온라인 조정, 컨텍스트 밴딧 확장(US 11,983,574 선행),
Firehose/Parquet 필드 경로, 다중 SUT·실기기 캘리브레이션, `C_serve`/`C_store` 계측.
