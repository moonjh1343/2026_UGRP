# 서버·클라이언트 환경 인지형 적응형 렌더링 전환 기법 연구

> 2026 POSTECH UGRP (연구프로젝트 트랙)

웹 페이지의 렌더링 방식(CSR / SSR / Streaming SSR / SSG·ISR / Islands)을 빌드 시점에 고정하지 않고, **요청 시점의 서버 부하와 클라이언트 환경을 입력으로 매 요청·세션마다 선택**하는 머신러닝 기반 정책을 설계하고 검증한다.

## 문제의식

렌더링 방식은 초기 로딩 지연, 상호작용 준비 시간, 서버 자원 소모에서 서로 다른 트레이드오프를 가진다. 그러나 대부분의 서비스는 라우트별로 하나의 방식을 정적으로 고정하며, 이는 다음을 반영하지 못한다.

- 같은 페이지라도 **저사양 단말**에서는 하이드레이션 비용이, **저대역폭 환경**에서는 전송 바이트 수가 지배적이다.
- 서버 부하가 급증한 시점의 SSR은 TTFB를 악화시켜, **평시에 최적이던 선택이 피크 시간에는 최악이 된다.**
- 사용자 환경 분포는 서비스·시간대·지역에 따라 계속 변한다.

즉 최적 렌더링 방식은 정적 상수가 아니라 **런타임 환경의 함수**라는 것이 이 연구의 출발점이다.

## 연구 질문

| | |
|---|---|
| **RQ1** | 관측 가능한 서버·클라이언트 특징만으로 렌더링 모드별 성능을 유의미하게 예측할 수 있는가? |
| **RQ2** | 예측 기반 동적 전환이 최적 고정 방식 대비 얼마나 개선되는가? 오라클(이론적 상한) 대비 몇 %를 달성하는가? |
| **RQ3** | 어떤 환경 세그먼트에서 개선폭이 가장 큰가? (가설: 저사양·저대역폭·고부하 구간) |
| **RQ4** | 특징 수집·추론 오버헤드가 개선폭을 상쇄하지 않는 실용적 구현이 가능한가? |

## 접근

**서로게이트 회귀 + argmin.** 모드를 직접 분류하는 대신 모드별 비용 `Ĵ(x, m)`을 예측하고 argmin을 취한다. 이 구조라야 상위 두 모드의 예측 차이가 작을 때 *"전환하지 않음"* 을 판단할 수 있다 — 모드 전환에는 캐시 파편화라는 고정 비용이 있으므로, 기대 이득이 그 비용을 넘을 때만 전환해야 한다.

**반사실(counterfactual) 문제의 2단계 해결.** 한 요청에는 한 모드만 적용되므로 "다른 모드였다면?"은 원래 관측할 수 없다. 이를 두 단계로 우회한다.

1. **랩 전수 실험** — 실험실 조건은 재현 가능하므로 동일 조건 벡터에 대해 **모든 모드를 측정**한다. 기기 등급(4) × 네트워크(5) × 서버 부하(4) × 라우트별 실행 가능 모드 + SSG의 캐시 상태(miss/hit/stale) = 10,400셀, 셀당 30회 반복.
2. **필드 무작위화** — 실트래픽 5~10%에 모드를 무작위 배정하고 배정 확률을 함께 기록하여, 편향 없는 로그로 오프폴리시 평가(IPS/DR)를 수행한다.

**서버 부하는 외생적으로 고정한다.** 렌더 모드 자체가 서버 부하를 바꾸는데 그 부하가 다시 입력 특징이므로, k6 배경 부하로 목표 CPU를 고정한 상태에서 측정 요청 하나를 얹어 잰다.

**추론은 엣지 인프로세스로만.** 추론 지연이 곧 TTFB 증가분이므로, LightGBM 앙상블을 단일 결정트리로 증류해 Lambda@Edge에서 평가한다. 목표 오버헤드는 **TTFB 증가 < 2ms**이고, 배포된 트리(깊이 12)의 실측은 p95 0.025ms다.

## 실험 인프라

AWS CDK로 정의된 5개 평면. 서버 환경과 클라이언트 환경을 각각 독립적으로, 재현 가능하게 조절하는 것이 핵심 요구사항이다.

| 평면 | 제안서 설계 | 구현된 것 |
|---|---|---|
| SUT | ECS Fargate의 Next.js(App Router) — 5개 모드를 단일 코드베이스로 구현, task 스펙이 실험 변수 | 완료. 랩 경로에는 ALB·CloudFront를 두지 않는다 |
| 클라이언트 측정 | AWS Batch + Playwright/CDP 에뮬레이션(95%), 5개 리전 실측 RTT, Device Farm 실기기 보정(5%) | Playwright/CDP 워커 완료. 실측 RTT·Device Farm은 미구현 |
| 부하 주입 | Fargate Spot의 k6 — 목표 CPU까지 VU 이진 탐색 캘리브레이션 | 완료. 로컬에는 같은 프로필을 읽는 Node 생성기 |
| 데이터 | web-vitals → Kinesis Firehose → S3(Parquet) → Glue/Athena | 랩 경로는 워커가 S3에 NDJSON 직접 기록. Firehose는 필드 경로용으로 미구현 |
| 학습·서빙 | SageMaker → Model Registry → AppConfig → Lambda@Edge | 로컬 LightGBM → 증류 트리를 엣지 번들에 굽는다. SageMaker·AppConfig 없음 |

**세 갈래의 이탈은 의도된 것이고 각 하위 `README.md`에 근거가 있다.** 랩 수집 경로의 CDN은
캐시 상태 축(miss/hit/stale)을 관측하려고 만든 실험 변수를 교란한다. Lambda@Edge는
환경변수를 쓸 수 없어 AppConfig를 가리킬 방법이 없고, 콜드 스타트마다 요청 경로에 왕복이
얹힌다 — 모델 교체는 배포로 처리하고 즉시 대응은 서킷 브레이커가 맡는다. SageMaker는
파이프라인을 파일럿 슬라이스로 디버깅하는 동안에는 얻는 것이 없다.

### 지금까지 나온 것

**RQ1 — 조건에 따라 최적 모드가 실제로 갈린다.** QoE만 놓고 봤을 때 전 조건에서 이기는
모드는 없다: islands 30.6% / ssr 27.8% / stream 15.6% / ssg 13.3% / csr 12.6%로 갈리고,
**25개 라우트 전부가 조건에 따라 승자가 바뀐다.** 축별로도 방향이 뒤집힌다 — 콘텐츠형에서
csr은 lte에서 44% 최적이지만 3g-slow에서는 0%이고, ssg의 최적 점유율은 부하가 idle→high로
갈수록 8%→67%로 오른다. 고정 모드가 왜 손해인지의 실측 근거다.

**RQ2 — 학습된 정책이 모든 고정 모드를 이긴다.** 라우트 홀드아웃 400조건, λ=0.3 기준:

| 정책 | top-1 일치 | 평균 regret |
|---|---|---|
| fixed-csr | 21.2% | 0.763 |
| fixed-ssr | 15.2% | 0.495 |
| fixed-stream (프레임워크 기본값) | 10.5% | 0.914 |
| fixed-islands | 13.5% | 0.503 |
| 휴리스틱 규칙 | 24.5% | 0.447 |
| **서로게이트 (앙상블)** | **74.8%** | **0.041** |
| 증류 트리 (배포본) | 74.2% | 0.046 |

증류 트리는 앙상블 대비 R² 0.999이고 추론 p95는 0.025ms — 2ms 예산의 1.25%다.

**λ는 정말로 그림자 가격처럼 움직인다.** λ=0 → 0.3에서 서버 비용이 절반 아래로 떨어지고,
λ≥1이면 정책이 사실상 라우트 룩업으로 퇴화한다(문맥을 안 본다). Pareto 무릎이 0.3이라
배포본을 거기에 맞췄다. 깊이는 λ에 딸린 값이다 — 제안서의 depth 5는 λ=1에서만 충분하고,
λ=0.3에서는 문맥 상호작용 때문에 63%에 그쳐 12로 늘렸다.

**마진 폴백 τ의 근거도 데이터로 확인됐다.** top-1과 top-2의 J 차이 중앙값은 0.488이지만
**21.8%의 조건에서 0.1 미만**이다. 전환에는 캐시 파편화라는 고정비가 있으므로 이 구간에서는
바꾸지 않는 것이 옳다.

한계도 분명하다. 라벨의 `ServerCost` 중 `C_serve`·`C_store`가 **0 — 근사가 아니라 미계측**
이라 SSG의 요청당 서버 비용이 0으로 잡힌다. `fixed-ssg`가 SSG 가능 160조건에서 98.8%를
찍는 것은 이 편향을 포함해서 읽어야 한다(`training/README.md`).

수집 비용은 제안서 추정 $282–343 대비 실측 약 **$450**다(실패한 시도 5회의 유휴 과금 +
high 샤드 꼬리 1.5일 + 재개 9시간).
