# 정책 서빙 평면 (CloudFront + Lambda@Edge)

랩 수집은 워커가 `x-policy` 헤더로 모드를 강제 지정한다. 필드에서는 그럴 수 없다 —
**엣지가 결정한다.** 이 디렉터리가 그 결정 지점이다.

> **현재 상태(2026-08-21): 미배포.** `policy/model/tree.v0.json`은 8/19에 grid-v1 학습
> 트리(`trained-20260818T163155Z`, λ=0.3·깊이 12)로 교체됐지만, 이 번들은 아직 그 트리로
> 다시 빌드·배포되지 않았다. 트리를 번들에 굽는 구조라(아래 참조) **모델 교체는 곧
> 재배포다** — `npm run build -- --origin https://<origin>` 후 `ServingOrigin` →
> `Serving` 순서로 올려야 한다. 논문의 CloudFront 캐시 적중률 수치가 여기에 걸려 있다.

## 캐시 키가 설계를 결정한다

CDN 뒤에서 렌더 모드를 고르려면 먼저 답해야 하는 질문이 있다: **모드가 캐시 키에
들어가는가?**

들어가지 않으면 정책이 무의미하다. 첫 요청이 SSG로 채운 캐시를, 저사양·저대역
기기가 그대로 받는다. 결정은 했지만 아무 효과가 없다.

그렇다고 모드를 그대로 키에 넣으면 반대 문제가 생긴다. 모드는 기기·네트워크·서버
부하의 함수이고 그 조합은 사실상 연속이라, 캐시가 요청마다 갈라져 히트율이 0에
수렴한다. 제안서 §3.2가 "전환에는 캐시 파편화라는 고정비가 있다"고 한 것이 바로 이것이다.

그래서 **정규화된 버킷을 키에 넣는다.**

```
뷰어 요청  (모든 요청)      Client Hints → 버킷 문자열 → x-ugrp-bucket
캐시 키                     URL + x-ugrp-bucket
오리진 요청 (캐시 미스에만)   버킷 + 라우트 + 서버 상태 → 모델 → x-render-mode
```

버킷은 `기기등급(4) × 유효네트워크(4) × 봇여부(2) × 데이터절약(2)` = 라우트당 최대 64개다.
같은 버킷의 요청은 같은 캐시 항목을 공유하고, 그 항목이 어떤 모드로 렌더됐는지는
채워질 때 결정된다.

## 왜 결정이 오리진 요청에 있는가

**제안서 §4.1은 Lambda@Edge를 뷰어 요청에 두는 것으로 읽히지만, 여기서는 오리진
요청이다.** 근거:

1. 뷰어 요청에서 모델을 돌리면 **캐시 히트에도 추론 비용이 붙는다.** 캐시 히트는
   결정할 것이 없다 — 응답이 이미 특정 모드로 렌더돼 있다. 히트율이 높을수록
   순수한 낭비가 된다.
2. 오리진 요청은 캐시 미스에서만 돈다. 그 경로는 어차피 오리진 렌더(수십~수백 ms)가
   지배하므로, 추론 2ms 예산이 훨씬 여유롭다.
3. 뷰어 요청은 패키지 1MB·메모리 128MB 제한이 있다. 오리진 요청은 50MB다.

뷰어 요청에는 모델이 필요 없는 정규화만 남기고, **CloudFront Function**으로 돌린다 —
Lambda@Edge보다 한 자릿수 싸고 서브밀리초다. 모든 요청에서 도는 코드에는 그쪽이 맞다.

개인화 라우트는 애초에 캐시되지 않으므로(`Cache-Control: private`) 오리진 요청이
매 요청 돈다. 결정이 가장 중요한 라우트에서 결정이 매번 일어난다.

## 모델을 번들에 굽는다 — AppConfig가 아니라

제안서 §4.1은 AppConfig가 트리를 배포하는 그림이다. Lambda@Edge에서는 성립하지 않는다:

- **환경변수를 쓸 수 없다.** AppConfig 애플리케이션·환경 ID를 넣을 곳이 없어 어차피
  번들에 굽어야 한다.
- **AppConfig Lambda 확장을 붙일 수 없다.** 직접 HTTP를 치면 새 실행 환경마다 그
  왕복이 요청 경로에 얹힌다. 엣지 로케이션이 수백 개라 콜드 스타트가 드물지 않다.
- 실행이 응답 후 동결되므로 백그라운드 갱신이 안정적이지 않다.

그래서 트리(`policy/model/tree.v0.json`, 현재 687KB — 오리진 요청의 50MB 한도에 비하면
여유롭다)를 번들에 포함하고, **모델 교체를 배포로 취급한다.** 대가는 전파 시간(수 분)이고, 얻는 것은 요청 경로에 네트워크 호출이
하나도 없다는 것이다. 정책 오작동에 대한 즉시 대응은 AppConfig가 아니라 서킷
브레이커가 맡는다 — 그쪽이 원래 그 역할이다.

## 구성

| 파일 | 역할 |
|---|---|
| `src/viewer-request.js` | CloudFront Function. Client Hints → 버킷 |
| `src/origin-request.mjs` | Lambda@Edge. 정책 계층 호출 → `x-render-mode` |
| `build.mjs` | esbuild 번들. 정책 계층을 **복사하지 않고** 임포트한다 |
| `test-edge.mjs` | `npm test` — 실제 AWS 없이 핸들러를 돌린다 |

정책 로직은 여기 없다. `apps/benchmark/policy/`가 원본이고 이 디렉터리는 어댑터다 —
CloudFront 이벤트를 `RequestLike`로 바꾸고, 결정을 헤더로 바꾼다. 로직을 옮겨 적으면
랩에서 검증한 것과 필드에서 도는 것이 갈린다.

## 상관 ID

**무결성상 가장 중요한 경로다.** 결정은 엣지에서, 측정은 브라우저에서 일어난다.
두 레코드를 조인할 수 없으면 데이터셋이 무가치하다.

오리진 요청 핸들러가 `x-correlation-id`를 만들어 오리진에 넘기고, 앱이 그 값을 비콘에
싣는다. 캐시 히트에서는 오리진 요청이 돌지 않으므로 cid가 새로 생기지 않는다 —
그 요청은 애초에 새로운 결정이 아니다.

## 필드 무작위화

트래픽의 일부를 무작위 모드로 보내고 **성향 점수(propensity)를 함께 기록한다**
(제안서 §5.5). 이게 없으면 수집된 필드 데이터가 전부 현재 정책의 선택에 편향되어
오프폴리시 평가가 불가능하다. 비율은 `config.js`의 `EXPLORE_RATE`.
