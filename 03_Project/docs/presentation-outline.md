> 런타임 컨텍스트 적응형 렌더링 모드 선택 — 서로게이트 회귀 기반 정책의 학습과 엣지 서빙

- **가정:** 발표 20분 + 질의응답 10분. 청중은 웹 렌더링을 깊이 알지는 못하는 CS 전공 심사위원
- **흐름:** 문제 → 아이디어 → 데이터 → 모델 → 서빙 → 결과 → 한계 (18장)
- **수치 출처:** 본수집 `grid-v1`(2026-08-14 → 08-17, 10,400셀·311,108행), `training/reports/grid-v1*.json`,
  배포 트리 `trained-20261117T152525Z`(조건 중심화 깊이 8). 수치는 [paper-draft.md](paper-draft.md)와 일치한다.

## Ⅰ. 도입 (3분)

### 1. 제목 (15초)

- **화면:** 제목 전문, 팀명·소속·날짜, 지도교수
- **말할 것:** 없음. 바로 2장으로 넘어간다.

### 2. 한 문장 요약 (45초)

- **화면:** 큰 글씨로 "웹 페이지를 어떻게 그릴지를, 빌드할 때 한 번 정하지 말고 요청마다 상황을 보고 고르자"
- **시각 자료:** 같은 `/dashboard` URL 요청이 둘로 갈라지는 그림
  - 고사양 기기 + 4G → CloudFront → `x-render-mode: csr`
  - 저사양 기기 + Save-Data → CloudFront → `x-render-mode: islands`
- **말할 것:** "실제 AWS 배포(2026-08-23)에서 응답 헤더로 확인한 결과입니다. 어떻게 이렇게 되는지
  보여드리고, 마지막에 다시 돌아오겠습니다."

### 3. 배경: 렌더링 모드 다섯 가지 (1분)

| 모드 | 일을 하는 곳 | 비용이 쌓이는 곳 |
|---|---|---|
| CSR | 브라우저가 JS로 전부 그림 | 클라이언트 CPU, 번들 다운로드, 추가 왕복 |
| SSR | 서버가 요청마다 HTML 완성 | 서버 CPU, TTFB가 부하에 노출됨 |
| Streaming SSR | 서버가 셸부터 흘려보냄 | 서버 CPU (첫 바이트는 빠름) |
| SSG·ISR | 빌드 때 미리 만든 HTML | 캐시 상태에 종속됨 (miss·stale) |
| Islands | 서버 HTML + 상호작용 부분만 하이드레이션 | 서버 CPU (하이드레이션은 적음) |

- **핵심 메시지:** 어떤 모드도 비용을 없애지 못하고, 어디로 옮길지만 정한다.
- **청중 배려:** 하이드레이션은 "서버가 만든 HTML에 JS를 붙여 클릭할 수 있게 만드는 과정"이라고 한 줄로 설명한다.

### 4. 문제 제기 (1분)

- **화면 위쪽:** 지금의 프레임워크는 라우트마다 모드를 **빌드할 때** 고정한다 (Next.js 설정 한 줄 예시).
- **화면 가운데:** 최적 모드를 바꾸는 세 요인
  - 느린 폰 → 서버가 그려 주는 편이 유리
  - 바쁜 서버 → 브라우저나 캐시에 넘기는 편이 유리
  - 느린 네트워크 → 바이트 수와 왕복 횟수가 지배
- **화면 아래쪽:** 연구 질문
  - 메인: 최적 모드를 (페이지 × 기기 × 네트워크 × 서버 부하)의 함수로 학습해 요청마다 고를 수 있는가?
  - **RQ1** 최적 모드가 실제로 조건에 따라 바뀌는가?
  - **RQ2** 학습한 정책이 고정 모드·휴리스틱보다 잘 고르는가? QoE와 서버 비용은 어떻게 맞바꾸는가?
  - **RQ3** 엣지에서 TTFB +2ms 안에, CDN 캐시를 깨지 않고 서빙할 수 있는가?

## Ⅱ. 문제 정식화 (3분)

### 5. 무엇을 최소화하는가 (1분)

- **화면:** 식 두 줄과 각 항을 가리키는 화살표 설명

  ```
  mode* = argmin_{m ∈ M(r)} Ĵ(x, m)        ← 가능한 모드 중 예측 비용이 가장 낮은 것
  J = Σ wᵢ · z_r(QoEᵢ) + λ · ServerCost    ← 사용자 체감 + 서버 비용의 환율
  ```

- **세부 정의:**
  - `x`: 기기 등급, 네트워크 유형, 서버 CPU·이벤트 루프 지연, 라우트 특성
  - QoE 가중치: LCP 0.4, INP 0.3, TBT 0.2, TTFB 0.1 (Core Web Vitals의 상대 비중)
  - `M(r)`: 라우트별 실행 가능한 모드 집합. dashboard·form·personalized에서는 SSG 불가.
    불가능한 모드를 고르면 조용히 대체하지 않고 `infeasible`로 기록한다.
- **말할 것:** "점수가 낮을수록 좋습니다. λ가 크면 서버를 더 아끼고, 작으면 사용자 체감을 더 챙깁니다."

### 6. 세 가지 설계 결정 (1분)

| 결정 | 이유 | 근거 |
|---|---|---|
| 분류가 아니라 비용 회귀 + argmin | 상위 모드들이 근소한 경우가 많고, 1·2등 격차(마진)가 "바꿀 가치가 있나"를 판단하는 정보 | 조건의 **21.8%가 마진 0.1 미만**. 모드 전환에는 캐시 분할이라는 고정 비용이 있다 |
| 라우트별 z-score | 생략하면 모델이 "무거운 페이지 = 나쁨"만 배움 | 페이지 간 LCP 스케일 차이가 모드 간 차이를 덮는다 |
| λ = 서버 비용의 그림자 가격 | 서버 예산 제약 아래 QoE 최소화 문제로 재정식화 | 운영자는 λ가 아니라 예산 `E[ServerCost] ≤ B`를 정하고, λ는 이중 상승법으로 따라온다 |

### 7. 핵심 난제: 반사실 (1분)

- **시각 자료:** 사용자 한 명에게 모드 A만 준 로그. "B였다면?" 칸은 물음표
- **두 가지 문제:**
  - 관측 불가: 한 요청에는 결과가 하나뿐이다.
  - 교란: 기존 배정은 무작위가 아니다(무거운 페이지에만 SSR을 쓰는 식). 로그 비교는 편향된다.
- **해결:** 실험실에서 조건을 재현할 수 있으니, **같은 조건 벡터에서 가능한 모든 모드를 측정한다**(완전 요인 실험).
- **덧붙일 한 줄:** 그래서 랩 regret은 추정치가 아니라 정확한 값이다. 필드로 넘어갈 때는 5% 무작위
  탐색과 오프폴리시 평가가 필요하다(18장).

## Ⅲ. 시스템과 데이터 수집 (5분)

### 8. 전체 아키텍처 (1분)

- **시각 자료:** 5개 평면 다이어그램. 상관 ID 조인 화살표는 빨간색으로 강조

  ```
  [SUT: Next.js 5모드] ← [측정 워커: Playwright+CDP] ← [부하 생성기]
          ↓ 상관 ID 조인
  [S3 / DynamoDB] → [학습: LightGBM → 증류 트리] → [엣지: CloudFront + Lambda@Edge]
  ```

- **말할 것:**
  - 측정 경로와 서빙 경로가 **같은 결정 계층(`policy/`)을 공유한다.** 실험한 정책과 배포한 정책이 같은 코드다.
  - 렌더 결정은 서버·엣지에서, 측정은 브라우저에서 일어난다. 두 기록을 잇지 못하면 데이터셋은 쓸모가 없다.
- **질의응답 대비:** 랩 수집 경로에는 CloudFront가 없다. CDN이 캐시 상태 축을 지워버리기 때문이다.

### 9. 측정 대상 앱 SUT (1분)

| 유형 | 무거운 축 |
|---|---|
| content | HTML 바이트 |
| list | 반복 컴포넌트 수 |
| dashboard | 하이드레이션 CPU |
| form | 상호작용 |
| personalized | 캐시 불가 |

- 유형마다 지배 축 하나만 흔든 라우트 **25개**
- **메커니즘:** 컴포넌트 트리는 하나, `'use client'` 경계를 어디에 긋느냐로 다섯 모드를 만든다.
- **검증:** `check:dom`으로 다섯 모드의 최종 DOM이 동일한지 확인한다. 모드 차이가 곧 렌더링 방식 차이라는 보장이다.
- **시각 자료:** 같은 트리에 경계선 다섯 개를 겹쳐 그린 그림

### 10. 실험 그리드 (1분)

- **화면 위쪽, 셀의 정의:** 측정 단위 = 셀 = (기기, 네트워크, 서버 부하, 라우트, 모드, 캐시 상태),
  셀마다 30회 반복. 정의는 버전 관리되는 코드(`workers/lib/grid.mjs`)에 있다.
- **화면 가운데, 축 표:**

| 축 | 수준 | 구현 |
|---|---|---|
| 기기 (4) | flagship 1× / mid 2× / low 4× / very-low 6× | CDP CPU 스로틀 + tier 헤더 주입 |
| 네트워크 (5) | 5G 100Mbps·10ms / LTE 25Mbps·50ms / 3G-fast 1.6Mbps·150ms / 3G-slow 0.4Mbps·400ms / offline-first 0.25Mbps·900ms | CDP 네트워크 에뮬레이션 (지연은 RTT) |
| 서버 부하 (4) | idle / 30% / 50% / 70% CPU | 별도 생성기(k6)로 고정, 측정 요청 하나만 얹음 |
| 모드 | 라우트별 실행 가능 모드만: SSG 가능 10개 × 5 + 불가 15개 × 4 = Σ\|M(r)\| **110** | 불가능한 조합은 셀을 아예 만들지 않음 |
| 캐시 상태 | SSG 셀만 miss / hit / stale로 분할 → SSG 라우트 10개 × 추가 2 = **+20** | 반복마다 상태를 맞추고 `x-nextjs-cache`로 확인 |

- **화면 아래쪽, 계산:**

  ```
  4 × 5 × 4 = 80조건 × (110 + 20) = 10,400셀 × 30회 → 311,108행
  ```

- **말할 것:**
  - "같은 조건에서 가능한 모든 모드를 실제로 쟀습니다. 그래서 조건마다 정답(oracle) 모드를 직접 알 수
    있고, 7장의 반사실 문제를 이렇게 피합니다."
  - 직렬로는 813시간. AWS Fargate 20샤드로 나눠 8/14~8/17, 약 3일에 수집했다.
  - 샤드 하나 = (SUT + 부하 생성기 + 워커) 한 세트. 샤드끼리 아무것도 공유하지 않는다.
    같은 SUT를 두 워커가 때리면 부하 수준이 깨진다.
  - 샤드 하나는 부하 수준 하나만 맡고(VU 수가 수준별 캘리브레이션 값), 셀 개수가 아니라 예상
    소요 시간으로 나눈다. stale 반복은 재검증 창을 기다리느라 62초로, 다른 반복(5초)의 12배다.
  - 셀 순서는 시드로 섞는다. 순서대로 돌리면 시간에 따른 인프라 드리프트가 특정 모드에 몰린다.
- **각주:**
  - offline-first는 완전 오프라인이 아니라 "오프라인 우선 설계가 필요할 만큼 열악한 망"이다(완전 오프라인은 페이지가 뜨지 않아 측정 불가).
  - 부하 상한 70%는 단일 프로세스 서버의 포화점이다(제안서 30/65/90%에서 재정의). high 셀은 실측 63–69%.
  - 계획 312,000회 대비 311,108행: high 부하에서 비콘이 오기 전에 타임아웃되는 반복이 있어 high 셀 평균 n은 29.69, 최소 21.
- **시각 자료(선택):** 셀 하나를 큐브의 한 칸으로 그린 3축(기기 × 네트워크 × 부하) 그림. 칸마다 모드 막대가 4–5개 서 있다.

### 11. 측정을 믿을 수 있게 만든 장치 (1분 30초)

| 장치 | 없으면 |
|---|---|
| 외생 부하 (생성기로 고정, 오토스케일 끔) | 모드가 부하를 바꾸고, 그 부하가 다시 특징이 되는 순환 |
| 조건 헤더 주입 (`x-cell-device-tier` 등) | CDP 스로틀이 Client Hints를 안 바꿔서 기기·네트워크 특징이 상수 |
| 캐시 상태 셀 변수화 (`x-nextjs-cache` 관측, 다르면 그 반복은 버림) | SSG의 hit와 miss가 한 셀에 섞임 |
| 상관 ID (Server-Timing 헤더) | 캐시된 페이지에서 서버 기록과 비콘이 조인 안 됨 |
| 순서 무작위화 · 시드 기록 · 이미지 다이제스트 고정 | 인프라 드리프트가 특정 모드에 몰림, 재현 불가 |

### 12. 조용한 실패에서 배운 것 (30초, 시간이 모자라면 생략)

- 에러 없이 그럴듯한 숫자를 내는 버그가 가장 비쌌다.

| 실패 | 겉보기에는 정상이었던 이유 |
|---|---|
| 헤드리스 Chrome이 봇으로 분류돼 모든 측정이 SSR로 고정 | `check:policy`가 SSR 대 SSR을 비교하며 통과 |
| 짧은 버스트로 부하를 맞추니 지속 CPU가 12–16%p 낮게 나옴 | 부하 축에 서버가 실제로 겪지 않은 CPU 값이 붙음 |
| CDN 정책이 엣지 결정 헤더를 지워 오리진이 자기 정책을 실행 | 200 응답, 그럴듯한 모드와 마진. 클라이언트가 바뀌어도 마진만 안 움직임 |

- **메시지:** 연구용 시스템에서는 "제대로 측정되고 있는가"를 검증하는 장치가 결과만큼 중요하다.
  그래서 단계마다 검증 게이트(`check:*`)를 두었다.

## Ⅳ. 모델과 서빙 (3분)

### 13. 서로게이트 모델 (1분 30초)

- **시각 자료:** 특징 x와 모드 m → 모델 → 모드별 Ĵ 막대 5개 → 가장 낮은 막대에 체크
- **화면, 모델:**
  - 모드를 **입력 특징**으로 넣은 회귀 모델 하나가 모든 모드를 같은 잣대로 채점한다.
    입력 24개(모드 1 + 클라이언트 7 + 세션 3 + 서버 상태 5 + 라우트 정적 특성 8).
  - 레이블 J = 라우트별 z-score QoE 가중합 + λ(0.3) × 서버 렌더 비용(ms)
  - LightGBM 5개 시드 앙상블 × 부스팅 200라운드(bagging으로 시드마다 다른 모델)
  - 손실 = MSE + α·(같은 조건, 다른 모드 쌍의 순위 힌지), α 0.3·ε 0.1. 절대값과 순서를 함께 맞힌다.
- **화면, 학습 데이터 규모:**

| | 학습 (J로 학습) | 검증 (평가만) |
|---|---|---|
| 라우트 | **20** | 5 (`content-03`·`dashboard-05`·`form-02`·`form-05`·`list-03`) |
| 조건 | 1,600 | 400 |
| 셀 | 8,320 | 2,080 |
| 행 | **248,886** | 62,222 |

- **말할 것:**
  - "J를 직접 학습하는 건 앙상블이고, 학습 데이터는 약 25만 행입니다. 검증은 학습에서 한 번도
    보지 못한 라우트 5개, 즉 새 페이지에서 모드를 잘 고르는지를 봅니다."
  - "행은 많지만 같은 셀의 30회 반복은 같은 입력에 노이즈 레이블 30개입니다. 실질적으로 배우는
    고유한 점은 8,320셀, 모드끼리 순위를 비교하는 그룹은 1,600조건입니다."
  - "일반화의 병목은 행 수가 아니라 라우트 20개입니다. 라우트 특징을 빼면 regret이 0.037에서

- **각주:**
  - 완전 요인 구조라 시간 분할은 라우트 그룹 분할로 퇴화한다(18장 한계).

  - 검증 라우트에 personalized 유형이 없다 — 본 적 없는 personalized 페이지에서의 성능은 미검증.
  - J는 λ에 따라 달라지므로 λ 스윕은 값마다 앙상블을 새로 학습한 결과다.
  - 증류 트리(14장)는 J가 아니라 같은 학습 행에 대한 앙상블 예측을 타깃으로 학습한다.

### 14. 증류와 엣지 서빙 (1분 30초)

- **화면 왼쪽, 증류:**
  - **왜:** 앙상블(트리 1,000개)은 엣지 번들 한도(1MB)·지연 예산(2ms)·JS 런타임에 맞지 않는다.
    결정 트리 하나가 앙상블의 **예측값**을 따라 하게 한다. 원래 J로 직접 학습하면 앙상블이 걸러낸
    측정 노이즈를 트리가 다시 주워 담는다.
  - **조건 중심화:** 조건마다 기준 수준(모드별 평균의 평균)을 빼고 그 잔차를 타깃으로 쓴다.

    ```
    조건 A:  Ĵ(csr)=1.0  Ĵ(ssg)=3.0  Ĵ(ssr)=5.0  →  수준 3.0  →  타깃 −2, 0, +2
    ```

    같은 조건 안에서 같은 값을 뺐으니 argmin과 마진은 그대로다. 대신 트리가 결정에 쓰이지 않는
    "이 조건이 전반적으로 비싼가"에 분기를 쓰지 않는다.
  - **깊이 선택 (λ=0.3, 앙상블 regret 0.041):**

| 타깃 | 깊이 | top-1 | regret | R² | 잎 | 크기 |
|---|---|---|---|---|---|---|
| 원 타깃 (제안서 계획) | 5 | 63.0% | 0.131 | 0.858 | 32 | |
| 조건 중심화 | 5 | 65.8% | 0.066 | 0.922 | 32 | |
| 원 타깃 | 12 | 73.2% | 0.049 | 0.996 | 2,547 | 640KB |
| **조건 중심화 (배포)** | **8** | **71.2%** | **0.049** | **0.985** | **255** | **52KB** |

- **화면 오른쪽, 서빙 흐름:**

  ```
  브라우저 ─① CloudFront Function ─② 캐시(URL + 버킷) ─┬─ 히트 → 응답 (추론 0)
                                                     └─ 미스 → ③ Lambda@Edge → ④ ALB+SUT
  ```

  - ① 모든 요청: Client Hints를 버킷 `기기-네트워크-봇-데이터절약`으로 접는다(4×4×2×2 = 라우트당 최대 **64개**).
  - ② 캐시 키 = URL + 버킷. 히트면 이미 결정된 응답이라 추론 비용 0
  - ③ 캐시 미스만: 버킷 + 서버 상태(30초 캐시) + 라우트 특성 → 모드마다 트리 실행 → argmin →
    가드 체인 → `x-render-mode`. 결정 계층 p95 **0.050ms**(예산의 2.5%)
  - ④ SUT가 그 모드로 렌더. 상관 ID가 Server-Timing으로 브라우저 비콘까지 이어진다.
- **화면 아래, 안전장치 한 줄:** 크롤러는 SSR 고정 · 하이드레이션 오류 2%나 5xx 1%를 넘으면 서킷
  브레이커가 Streaming SSR로 복귀 · 마진 τ 미만이면 전환하지 않음 · 5% 무작위 탐색과 성향 점수 기록
- **말할 것:**
  - "깊이 8과 12는 regret 차이가 없습니다(쌍 부트스트랩 95% CI [−0.013, 0.012]). 그래서 크기가
    1/12인 쪽을 배포했습니다. 틀릴 때도 근소한 2등을 고르기 때문에 pairwise는 오히려 더 높습니다
    (80.3% 대 78.0%)."
  - "핵심은 캐시 키입니다. 모드를 키에 안 넣으면 첫 요청이 CSR로 채운 캐시를 저사양 기기도
    받고, 조건을 그대로 넣으면 캐시가 요청마다 갈라집니다. 버킷 64개가 그 중간입니다."
  - "결정은 캐시 미스일 때만 합니다. 히트는 결정할 게 없고, 미스 경로는 어차피 오리진 렌더가
    수십~수백 ms라 0.05ms는 보이지 않습니다."
- **각주:**
  - 이전 배포본(깊이 12)은 증류 교사 예측에 검증 행이 섞여 수치가 낙관적이었다(74.2% → 수정 후 73.2%).
    지금은 학습 행 248,886개만 쓴다.
  - 실행 불가능한 모드는 채점하지 않는다. 개인화 라우트에서 SSG를 채점하면 캐시 히트 가정 때문에 항상 최소가 되어, 로그에 없는 손실처럼 남는다.
  - 버킷 결측값: 기기 등급은 3, 네트워크는 4g. 힌트를 안 보내는 브라우저(Safari 등)를 최저 사양으로 몰지 않기 위해서다.
  - 왜 origin-request인가: viewer-request에서 돌리면 캐시 히트에도 추론 비용이 붙는다. 개인화 라우트는 `private`이라 매번 결정한다.
  - 왜 번들에 굽나: Lambda@Edge는 환경변수와 AppConfig 확장을 못 쓴다. 모델 교체 = 배포(전파 수 분), 긴급 대응은 서킷 브레이커가 맡는다.
  - 위조 방지: 뷰어 함수가 클라이언트가 보낸 버킷과 엣지 전용 헤더를 덮어쓰거나 지운다. ALB는 CloudFront 대역만 받는다.
  - 성향 점수: 탐색 `0.05/후보 수`, 정책 선택 `0.95 + 0.05/후보 수`, 하드 고정 정확히 `1`
  - 콜드 스타트 직후 첫 요청은 서버 상태 캐시가 비어 있어 `cpuPct` 등이 0인 상태로 결정된다.
  - 8/23 실배포 검증은 이전 깊이 12 트리로 했다. 깊이 8 서빙에는 SUT 이미지와 엣지 번들 재빌드·재배포가 필요하다.
- **시각 자료(선택):** 왼쪽은 앙상블 1,000트리 → 트리 1개 깔때기, 오른쪽은 위 요청 흐름 다이어그램.
  두 장으로 나누면 증류 표와 흐름도를 크게 보여줄 수 있다.

### 16. RQ2 — 학습한 정책은 얼마나 잘 고르는가 (1분 20초)

| 정책 | top-1 | 평균 regret |
|---|---|---|
| 항상 Streaming SSR (프레임워크 기본값) | 10.5% | 0.914 |
| 항상 CSR | 21.2% | 0.763 |
| 항상 SSR (가장 나은 고정 모드) | 15.2% | 0.495 |

- **말할 것:**
  - regret은 가장 나은 고정 모드의 **약 1/10**, 프레임워크 기본값의 약 1/19
  - regret 중앙값은 0. 틀린 경우도 대부분 2등과 차이가 거의 없다.
  - fixed-ssg는 가능한 곳에서는 거의 최적이지만 라우트의 40%에서만 가능하다. 정책의 가치는 SSG가 없는 60%에 있다.
- **용어 각주:** regret = 고른 모드의 비용 − 실측 최적 모드의 비용 (z 단위)

### 18. 한계와 향후 연구, 결론

**한계 (솔직하게)**

- 서버 비용에 렌더 CPU만 들어간다. 히트 응답 비용(`C_serve`)과 캐시 저장 비용(`C_store`)은 미계측(근사가 아니라 0).
- 랩에서는 특징 9개가 상수다: deviceMemory, hardwareConcurrency, saveData, 재방문, 이전 LCP·TBT,
  inflight, 캐시 적중률, 라우트 RPS. 모델이 아직 쓰지 못한다.
- 부하 상한 70%(단일 프로세스 포화점), TTFB에 에뮬레이션 RTT 미반영, 실기기 없이 CDP 에뮬레이션만, SUT 1개
- 절제 실험에서 쌍별 손실과 z-score의 효과는 뚜렷하지 않았다(라우트 홀드아웃 분할 탓으로 추정, 확인은 후속).

**향후 연구**

- 필드 트래픽의 5% 탐색 데이터로 오프폴리시 평가(IPS/DR). 장치는 이미 배포 코드에 있다.
- λ 온라인 조정(dual ascent), 앙상블 불확실성 기반 마진 τ
- 실기기 보정(Device Farm), 컨텍스트 밴딧 확장, 복수 SUT

**결론 (한 문장)**

> 렌더링 모드 선택을 "빌드 시점 설정"에서 "요청 시점의 학습된 결정"으로 바꿀 수 있고,
> 그 결정은 엣지에서 0.05ms 안에 내릴 수 있다.
