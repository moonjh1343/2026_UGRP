# 논문 목차 (안)

**제목(가안):** 머신러닝 기반 환경 적응형 하이브리드 웹 렌더링 최적화 프레임워크 연구
— 런타임 컨텍스트에 따른 렌더링 모드 선택 정책의 학습과 엣지 서빙

관련 문헌은 [references.md](references.md) 참조. 5장 수치는 6단계 본수집 `grid-v1`
(2026-08-14 시작, 8/16 기준 97%, 완료 후 학습 예정 — 아직 `v0-unfitted`)의 결과로 채운다.
`training/out/`은 스모크 테스트 산출물이므로 인용하지 않는다.
4장에 적을 실험 조건 중 제안서와 달라진 것: 부하 축 30/50/70% CPU(2 vCPU SUT 천장 ~71%,
`load/README.md`), high 수준의 실측 63.8–68.9%, high 셀의 n<30(비콘 미도착), 랩 경로에
ALB/CloudFront 없음(`infra/README.md`).

장 역할 구분: **3장(연구 내용)** 은 무엇을·왜 — 정식화, 설계 원리, 실험 설계, 판단 근거.
**4장(구현 방법)** 은 어떻게 — 실제 코드·인프라·절차·수치. 같은 주제가 두 장에 나오더라도
내용이 겹치지 않게 쓴다.

## 초록

## 1. 서론
- 1.1 배경 — 빌드 타임에 고정되는 렌더링 모드(CSR/SSR/SSG/ISR/Streaming SSR/Islands)
- 1.2 문제 제기 — 최적 모드는 디바이스·네트워크·서버 부하의 함수
- 1.3 연구 목적 및 연구 질문
  - RQ1 조건별 모드 우열이 실제로 갈리는가 (divergence)
  - RQ2 학습된 정책이 고정 모드·휴리스틱 베이스라인을 이기는가
  - RQ3 엣지 추론 오버헤드(TTFB < 2ms)와 캐시 효율을 유지하며 서빙 가능한가
- 1.4 기여 및 논문 구성

## 2. 관련 연구
- 2.1 렌더링 아키텍처와 CSR/SSR 성능 비교
- 2.2 적응형 콘텐츠 전달 (adaptive loading, Client Hints, RUM 기반 최적화)
- 2.3 학습 기반 시스템 최적화
- 2.4 오프폴리시 평가와 반사실(counterfactual) 문제
- 2.5 기존 연구와의 차별점

## 3. 연구 내용
- 3.1 문제 정식화
  - 3.1.1 컨텍스트 벡터 x, 라우트별 실행 가능 모드 집합 M(r)
  - 3.1.2 비용 함수 J(x, m) = QoE 비용 + λ·서버 비용
  - 3.1.3 제약 최적화와 λ의 shadow price 해석 (dual ascent)
  - 3.1.4 서로게이트 회귀 + argmin — 분류가 아닌 이유, top-1/top-2 마진과 전환 비용
  - 3.1.5 라우트별 z-score 정규화의 필요성
- 3.2 시스템 설계
  - 3.2.1 전체 아키텍처 — 5개 플레인 (SUT / 클라이언트 측정 / 부하 주입 / 데이터 / 학습·서빙)
  - 3.2.2 결정 계층 설계 — 하드 핀(크롤러·결제/인증), 서킷 브레이커, infeasible 폴백 기록
  - 3.2.3 엣지 서빙 설계 — `x-ugrp-bucket` 캐시 키, origin-request 시점 추론, 번들 내장 트리
  - 3.2.4 상관 ID 조인 — 데이터 무결성 경로
  - 3.2.5 계획서 대비 설계 변경과 근거 (SageMaker/AppConfig/Firehose/ElastiCache 미채택, 랩 경로 무-CDN)
- 3.3 실험 및 데이터 수집 설계
  - 3.3.1 반사실 문제와 full-factorial 랩 수집
  - 3.3.2 격자 정의 — 디바이스 4 × 네트워크 5 × 부하 4 × (Σ|M(r)|=110 + SSG 캐시 상태 20) = 10,400셀 × 30반복
  - 3.3.3 측정 지표(웹 바이탈 + 서버 렌더 CPU)와 라벨 정의, 서버 비용 측정 범위와 한계 (C_serve/C_store 미계측)
  - 3.3.4 필드 무작위화(5–10%)와 성향 로깅
  - 3.3.5 재현성 통제 원칙 — 조건 순서 무작위화, 시드·버전 기록, 시간·라우트 그룹 분할
- 3.4 학습 파이프라인 설계
  - 3.4.1 특징 벡터와 train-serve 정합성 (`features.ts` ↔ `config.py`)
  - 3.4.2 LightGBM 서로게이트 + pairwise 목적 함수
  - 3.4.3 depth-5 트리 증류
  - 3.4.4 평가 설계 — 지표(QoE 비용·서버 CPU·regret vs oracle·모드 전환률), 베이스라인(고정 모드 5종·Streaming SSR 기본값·휴리스틱), 오프폴리시 평가(IPS/DR)

## 4. 구현 방법
- 4.1 벤치마크 애플리케이션 (SUT)
  - 4.1.1 단일 코드베이스 5모드 라우팅과 공유 컴포넌트 그래프
  - 4.1.2 라우트 유형(content/dashboard/form/personalized 등)과 M(r)
  - 4.1.3 계측 — 서버 레코드·클라이언트 비콘, 결정론적 페이로드
- 4.2 데이터 수집 방법
  - 4.2.1 Playwright 워커와 CDP 에뮬레이션, Client Hints 주입 (`x-cell-device-tier`/`x-cell-effective-type`)
  - 4.2.2 병렬 수집 인프라 — 20샤드(SUT+k6+worker 삼중), 샤드 배정 규칙(`shard.mjs`), S3+DynamoDB 체크포인트·재개
  - 4.2.3 오케스트레이션과 감시 — Step Functions, watchdog, 실패 시 자동 축소
  - 4.2.4 격리(quarantine) 창과 재큐잉
- 4.3 변인 조절 방법
  - 4.3.1 클라이언트 축 — CPU 스로틀링·네트워크 에뮬레이션 프로파일
  - 4.3.2 서버 부하 축 — k6 VU 이진 탐색, 버스트 vs 지속 부하 캘리브레이션 편차, 30/50/70% 재정의 근거
  - 4.3.3 SSG 캐시 상태 축
- 4.4 결정 방법 (정책 서빙 구현)
  - 4.4.1 `policy` 패키지 경계와 특징 추출 (`features.ts`)
  - 4.4.2 CloudFront Function → Lambda@Edge 처리 흐름
  - 4.4.3 서버 상태 특징의 의도적 staleness(~30s)
- 4.5 검증 게이트 — `check:dom`·`join`·`divergence`·`policy`·`tree`·`determinism`; 조용히 실패하는 버그와 방어(봇 오분류, Client Hints 미주입, 특징 순서 드리프트, floating Promise)
