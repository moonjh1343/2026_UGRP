# 측정 워커

랩 전수 실험(제안서 §5.2)의 실행 계층. CDP로 기기·네트워크를 스로틀링하고, 상호작용을
주입하고, 앱의 비콘 파이프라인에서 지표를 조인해 온다.

배포에서는 AWS Batch/Fargate의 Playwright 워커가 Step Functions Distributed Map으로
셀 그리드를 나눠 받고 DynamoDB에 체크포인트를 남긴다. 여기 있는 것은 같은 구조의
단일 프로세스 판이다 — **셀 단위 재개 가능성**이 핵심이고 그 성질은 분산 여부와 무관하다.

## 실행

앱을 프로덕션 빌드로 띄운 상태여야 한다.

```bash
npm install

# 5단계 합격 기준 검사
node verify-variance.mjs --reps 30 --types content,dashboard,form

# 수집 (같은 --name으로 다시 실행하면 재개)
node run.mjs --name pilot --reps 30 --loads idle --types content
```

부하 셀(`--loads low,mid,high`)을 쓰려면 `load/calibrate.mjs`를 먼저 돌려야 한다.
캘리브레이션이 없으면 해당 셀은 **건너뛴다** — VU 수를 모른 채 부하를 걸면
"부하 65%" 셀이 실제로는 다른 부하이고, 셀 정의가 거짓이 된다.

부하는 **수준별로 묶어서** 건다. 부하 전환은 안정화에 수십 초가 걸리므로 셀마다 갈아끼우면
그 전이 구간이 측정에 섞이고 시간의 대부분을 안정화에 쓰게 된다. 대신 **부하 그룹 안에서는
반드시 무작위 순서**다.

## 구성

| 파일 | 역할 |
|---|---|
| `lib/grid.mjs` | 조건 그리드 · 시드 PRNG · 셔플. **버전 관리되는 실험 정의** |
| `lib/interactions.mjs` | 유형별 결정적 상호작용 시퀀스 (INP 유발) |
| `lib/measure.mjs` | 한 셀 1회 측정 — 스로틀링, 캐시 상태 통제, 비콘 조인 |
| `lib/stats.mjs` | 강건 통계 · MAD 이상치 제거 · 5단계 판정식 |
| `lib/checkpoint.mjs` | JSONL 체크포인트 (append-only) |
| `lib/env.mjs` | 브라우저·Node·Next·정책 버전과 시드 기록 |
| `run.mjs` | factorial 수집 실행기 |
| `verify-variance.mjs` | 5단계 합격 기준 검사 |

## 판정식

5단계 기준은 "반복 30회의 분산이 모드 간 차이보다 작은가"다.

```
분산비 = pooled_within_sd / (max_median − min_median) < 0.5     ← 합격 조건
분해능 = pooled_within_sd / (2위 − 1위)                          ← 진단
```

**"모든 모드 쌍이 분리되는가"를 기준으로 삼지 않는다.** 3단계 실측에서 대시보드·폼·개인화형은
상위 3개 모드가 실제로 노이즈 안에 있었고, 그것은 측정 실패가 아니라 참인 발견이다 —
그래서 마진 폴백 τ가 필요하다. 5단계가 물어야 하는 것은 "그런 결론을 내릴 만큼 반복
노이즈가 작은가"이지 "차이가 항상 존재하는가"가 아니다.

**분산비만 보면 안 된다.** CSR처럼 혼자 3배 떨어진 모드가 하나만 있어도 폭이 그것에
지배되어, 나머지가 전혀 구분되지 않아도 통과한다. 그래서 분해능과 인접 쌍 분리 수를
함께 보고한다.

## 손대기 전에 알아야 할 것

- **스로틀링은 네비게이션 전에 건다.** 후에 걸면 첫 바이트가 무제한 대역으로 와서
  TTFB와 LCP가 조건과 무관한 값이 된다.
- **CDP 스로틀링은 Client Hints를 바꾸지 않는다.** 워커가 `x-cell-*` 헤더로 실제 조건을
  주입해야 결정 계층이 보는 기기·네트워크가 상수로 굳지 않는다.
- **반복마다 새 컨텍스트.** 캐시·스토리지가 남으면 콜드와 웜이 한 셀 안에 섞인다.
- **반복 × 모드를 인터리빙한다.** 모드별로 30회씩 몰아 돌면 각 모드가 서로 다른 시간대를
  점유해, 그 시간대의 인프라 상태(열, GC, 캐시)가 모드 효과로 잘못 귀속된다.
- **SSG는 캐시 상태를 셀 변수로 고정한다.** 통제하지 않으면 한 셀 안에서 미스와 히트가
  섞여 분산이 폭발한다.
- **`stale`은 반복당 ~62초가 든다 — 감수하기로 했다.** 엔트리를 만든 뒤 revalidate 창(60초)이
  지나야 하고, stale 응답 한 번이 백그라운드 재생성을 유발해 반복마다 다시 기다려야 한다.
  총 24,000회로 직렬 413시간, 라우트 10-way 병렬에서 ~41시간이다.
  짧은 revalidate 변형을 두는 대안은 `T`가 다른 라우트를 만들어 `missRate`의 스케일을
  라우트마다 갈라놓는다 — 캐시 축을 도입한 목적이 그 항의 관측이라 택하지 않았다.
  **`--skip-stale`은 검증용 탈출구이지 수집 옵션이 아니다.**
- **같은 라우트의 stale 셀은 병렬화할 수 없다.** ISR 엔트리가 라우트 경로 단위로 공유되어
  두 워커가 서로의 stale 타이머를 리셋한다. 부하 수준도 SUT 전역 조건이라 직렬이다.
  병렬화 가능한 축은 SSG 라우트(10종)뿐이다.
- **상호작용에 `fill()`·`selectOption()`을 쓰지 말 것.** Playwright는 값을 CDP `Input.insertText`로
  넣는데, 이는 사용자 상호작용으로 집계되지 않는다(`interactionId` 없음,
  `performance.interactionCount` 증가 없음). 그러면 **INP가 통째로 결측된다.** 5단계
  스모크 테스트에서 폼형만 INP가 없었고, 하필 폼형의 지배 축이 INP였다.
  `click` + `pressSequentially`, select에는 `press('ArrowDown')`을 쓴다.
- **INP는 앱 쪽 폴백에도 의존한다.** `event` 타이밍은 durationThreshold 미만이면 엔트리가
  아예 전달되지 않아, 가벼운 위젯에서는 web-vitals가 아무것도 확정하지 못한다.
  `Beacon.tsx`가 임계값 16ms로 직접 관측하고, 그보다 빠른 경우는 `interactionCount`로
  "상호작용은 있었으나 임계값 미만"(INP=0)과 "상호작용이 아예 없었음"(결측)을 구분한다.
- **지표를 워커가 직접 재지 말 것.** `getEntriesByType`으로는 LCP도 롱태스크도 잡히지
  않는다. 앱의 비콘 파이프라인이 유일한 경로이고, cid로 조인되지 않은 반복은 버린다 —
  피처 없는 라벨은 학습에 쓸 수 없다.
- **측정 워커는 로컬호스트만 때려도 외부 네트워크에 오염된다.** 실행 중 NIC가 끊기면
  Chrome이 DNS·연결 재시도를 반복하고, 그 CPU가 스로틀링된 렌더러와 같은 코어를 두고
  경쟁한다. 5단계 재측정 한 번이 이렇게 통째로 망가졌다(값 3~5배, 순위 뒤섞임).
  `verify-variance.mjs`가 **드리프트**(지속적 변화)와 **스파이크 비율**(간헐적 사건)을
  함께 보고하는 이유다 — 둘을 구분하지 못하면 멀쩡한 앱을 고치기 시작한다.
- **환경이 바뀌면 재개하지 말 것.** 브라우저·Node·Next 버전이나 순서 시드가 이전 실행과
  다르면 `run.mjs`가 중단한다. 앞뒤 데이터를 같은 데이터셋으로 볼 수 없기 때문이다.
